# REPLIT MASTER WORK ORDER

## Hire’in AI Governance Layer — Phased Current-System Audit and Implementation-Readiness Assessment

# 1. Role

Act as a principal SaaS architect, enterprise solution architect, business analyst, security architect, AI-governance architect and senior codebase auditor.

You are auditing the existing Hire’in platform before the company designs and implements the **Hire’in AI Governance Layer**.

The CEO Copilot, Manager Performance Copilot and Employee AI Buddy will eventually operate through this Governance Layer.

This assignment is a **read-only audit and implementation-readiness assessment**.

Do not implement, refactor or repair production functionality during this assignment.

---

# 2. Program context

Hire’in already has a large operating platform containing many of the following capabilities:

* Employee profiles
* Organization hierarchy
* Departments, roles and levels
* Goals and KPIs
* Check-ins
* Training
* Probation
* PIP
* SOPs and policies
* Notifications and reminders
* Attendance and leave
* Payroll
* Approvals
* Employee questions and concerns
* Audit logs
* Staffing operations
* Sales
* Marketing
* Finance
* Reporting
* Existing AI integrations

Many modules already contain mini-automations and notifications.

The future Governance Layer must not rebuild working features unnecessarily.

It must determine:

1. Whether the existing process is complete
2. Whether hierarchy is enforced
3. Whether the required action occurred
4. Whether evidence is reliable
5. Whether the process reached closure
6. Whether the signal is safe to use in governance
7. Whether AI is required
8. Whether employee PII can remain protected
9. Whether the CEO needs a finding, recommendation or decision request

The future implementation will happen in vertical phases.

Therefore, this audit must produce findings that directly support those implementation phases.

# 4. Core audit objective

The audit must answer:

> Which existing Hire’in processes can reliably support governance today, which require targeted repair before use, which should be consolidated, and which new primitives must be designed?

The audit is not complete merely because modules and tables are listed.

It must trace the complete control chain:

```text
Business requirement
→ System trigger
→ Responsible person
→ Notification or task
→ Acknowledgement
→ Required action
→ Evidence
→ Validation
→ Escalation
→ Resolution
→ Closure
→ Audit record
```

Where the chain stops, identify the exact gap.

# 10. Signal Eligibility Gate

The future Governance Layer must not treat every existing record as a trustworthy governance signal.

For each workflow, determine its signal eligibility.

## `ELIGIBLE`

The signal may support governance findings and CEO reporting.

It must be:

* Verified active
* Backend-authorized
* Hierarchy-aware
* Measurable
* Evidence-linked
* Time-bounded
* Auditable
* Completion-tracked
* Exception-aware
* Data-quality checked

## `CONDITIONALLY_ELIGIBLE`

The signal may support informational reporting but not consequential findings.

## `SYSTEM_REMEDIATION_ONLY`

The workflow may generate a technical or process-control finding, but not an employee or manager performance finding.

## `INELIGIBLE`

The workflow must not feed the Governance Layer until repaired.

Example:

```text
Notification sent
+ No acknowledgement tracking
+ No action-completion tracking
+ No closure state
= SYSTEM_REMEDIATION_ONLY
```

The future system may conclude:

> The notification workflow is incomplete.

It may not conclude:

> The manager refused to complete the review.

---

# 11. Technical-debt classifications

Place each gap into one category.

## Category A — Critical blocker

Must be resolved before any Governance Layer implementation.

Examples:

* Restricted PII can reach an external AI provider
* Backend authorization weakness
* Cross-employee or cross-role data exposure
* Payroll-integrity risk
* Consequential actions without audit logging
* Secrets exposed in logs or client payloads

## Category B — Governance prerequisite

Must be fixed before the affected vertical slice goes live.

Examples:

* Manager hierarchy not enforced
* Action completion not tracked
* Goal evidence source missing
* PIP coaching not recorded
* Check-in closure state missing
* Employee dispute path absent

## Category C — Opportunistic repair

Repair when the related code path is already being changed, provided scope remains controlled.

Examples:

* Duplicate helpers
* Repeated notification formatting
* Inconsistent naming
* Local service consolidation
* Minor enum or validation cleanup

## Category D — Deferred debt

Document but do not include in the current Governance Layer program unless it later becomes a blocker.

Examples:

* Legacy inactive pages
* Cosmetic inconsistencies
* Unrelated broad refactors
* Historical modules not used by the pilot

# 50. Acceptance criteria

The audit is complete only when:

* Work is executed in four separate review-gated waves.
* Live code is treated as the primary source of truth.
* Every material claim has technical evidence.
* Schema or UI presence is not treated as end-to-end verification.
* Hierarchy enforcement is traced through backend APIs.
* Automation delivery is separated from action completion.
* Action completion is separated from resolution and closure.
* Signal eligibility is classified for every major workflow.
* Employee performance findings are not supported by incomplete system chains.
* Manager accountability is audited separately.
* PII and external-AI exposure are traced end to end.
* Existing AI usage is fully cataloged.
* Technical debt is classified by implementation relevance.
* Repair work is mapped to vertical implementation slices.
* Shared foundation repairs are separated from slice-specific repairs.
* The final design-input pack contains verified facts rather than assumptions.
* No production logic, configuration or data is modified.

Begin with Audit Wave 1 only.

Do not begin Wave 2 until Audit Wave 1 has been reviewed and approved.
