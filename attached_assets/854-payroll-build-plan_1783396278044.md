# #854 — Payroll Engine: Build Plan & Compliance Roadmap
### Companion to `854-payroll-engine-final-spec.md` (v2.0)
### Purpose: close every open gap, name every missing input, and set the bar for a top-1% HR tool
### Context: remote company · Delhi HQ · UP/Punjab/Bihar cluster (+ possible J&K/Ladakh)

> **How to read this.** The spec says *what* to build. This plan says *how* to build it, *in what
> order*, *what must be true before it ships*, and *what makes it feel like a best-in-class product
> rather than a functional one*. Three things drive everything below:
> **(1)** the task is now L-sized and splits into an engine ticket and a UI ticket;
> **(2)** ten gaps are resolved or flagged here — do not let the executor guess on any of them;
> **(3)** compliance is a hard gate, not a footnote — a perfect engine still remits wrong numbers
> off a stale seed table.

---

## 1. Scope split — two tickets, engine-first

The original was M-sized (engine + UI, one ticket). v2 roughly doubled it (two new schema tables, ESI
period logic, Labour Codes floor, StatutoryEngine interface, 30–50 golden vectors). Split it so the
compliance-critical path is never blocked behind a settings screen.

| Ticket | Contains | Exit criterion (Definition of Done) |
|---|---|---|
| **#854-A — Engine + Vectors** | `statutory_rates` + `state_deductions` + schema migrations · `computeComponentsFromGross` · `computeIndiaStatutory` (50% floor, PF caps/splits, ESI period logic) · `StatutoryEngine` interface · wiring into generate/regenerate · computation snapshot · golden test-vector suite | **Golden vectors pass against CA-confirmed expected outputs.** (Not "vectors pass" alone — the *expected values* need CA sign-off. This couples the CA gate to the engine, which is where it belongs.) |
| **#854-B — UI / PDF / Settings** | Salary Structures tab · rule builder + live preview · State Registrations panel · slip form auto-fill + override toggles · `salarySlipHtml.ts` earnings/deductions/employer sections · My Team assignment | Slip renders correctly for structured + unstructured + override cases; Settings round-trips all config; matches spec §7. |

**Why this order:** if the engine runs long, you don't want compliance blocked behind a Salary
Structures UI. #854-B can start once #854-A's engine interface is stable (the UI calls the engine),
but #854-A ships first and independently.

## 2. Resolved gaps (decisions — executor must not re-litigate)

Ten gaps. Each has a decision. Where a decision is a genuine owner call, it's marked 🟠 **OPEN** and
listed again in §3.

| # | Gap | Resolution |
|---|---|---|
| G1 | **PSDT applicability undefined** — "taxable income > exemption limit" can't be computed pre-TDS (circular). | Make the trigger a **configurable annual threshold on the `state_deductions` row** (`psdt_annual_threshold`), **not** a hard-coded ₹20,833/mo. The old-regime ₹2.5L prorate is regime-dependent and now stale (new regime is default, higher basic exemption + rebate). CA sets the conservative figure; engine just reads the config. Deduct PSDT for Punjab employees whose annualised gross ≥ threshold. |
| G2 | **ESI `esi_covered_until` has no backfill** — on first deploy all employees are NULL → engine reads "not covered" → silent under-deduction for the rest of the live contribution period. | **Mandatory one-time backfill migration** in #854-A: set `esi_covered_until = end of current contribution period` for all active employees with current gross ≤ ₹21,000 (₹25,000 if disability). Migration must **log the affected set** for manual review (employees currently > ₹21k but covered at period start can't be reconstructed — conservative backfill accepted, but surfaced not assumed). This is the single highest-risk gap. |
| G3 | **EPF admin charges have no home** — correctly fixed to ₹500/establishment min, but an *establishment-level* cost can't live on an *employee* slip. | **Exclude from per-slip computation output.** Explicitly **defer to the payroll-run summary in #855**. Note the cross-ticket dependency so #855 picks it up. |
| G4 | **`work_city` column purpose ambiguous** — never referenced in engine/UI. | **Keep with an explicit schema comment**: "Phase 3 — HRA metro/non-metro classification (50% vs 40% exemption) and future `pt_state` derivation." Collecting city now is free; Phase 3 needs it. Ambiguous columns without stated intent are how drift starts — the comment is the fix. |
| G5 | **Employer Contribution on employee slip is hardcoded** — showing EPF/EPS/EDLI/Employer ESI reveals total CTC; some firms hide it. | Add `show_employer_contribution_on_slip` (bool) in `system_settings`. **🟠 OPEN: default value.** Reviewer proposed `false`; the original ticket asked for it "for transparency," so defaulting `false` silently reverses a documented decision. **Recommendation: default `true` (honor the ticket), toggleable off.** Owner confirms. |
| G6 | **Flat statutory levies must not be LOP-prorated** *(surfaced in my review)* — spec says "deduction after LOP," but PSDT (₹200) and MH/KA/TG PT (₹200) are **flat** amounts owed if the slab is met; they don't scale with days worked. | Add `is_flat` (bool) to `state_deductions`. Flat levies → full amount if slab met, **no LOP proration**. Percentage/graded levies → prorate per existing rule. Without this, a half-month-LOP Punjab employee gets ₹200 wrongly shaved to ₹180. |
| G7 | **`workingDays` convention undefined** *(new)* — LOP = presentDays/workingDays, but "workingDays" is unspecified: calendar days? actual working days ex-weekends? fixed 26 (ESI/gratuity convention)? fixed 30? Different conventions change every LOP number. | **Define explicitly in #854-A as a company setting** (`lop_basis`: `calendar_days` | `fixed_26` | `fixed_30` | `actual_working_days`), default **`actual_working_days`** for the pay month. Document the chosen semantics in the slip formula output so the number is explainable. CA confirms the default matches your policy. |
| G8 | **Rounding convention under-specified** *(new)* — "nearest rupee" everywhere, but EPF has specific statutory rounding (round-up on employee share in some interpretations) and the residual absorber must reconcile to the paise. | Specify per-line: statutory deductions **rounded to nearest rupee** (confirm EPF round-up with CA), Special Allowance residual **absorbs the sub-rupee remainder** so Earnings sum to gross exactly. Add a golden vector that asserts the reconciliation at a value that produces a rounding conflict. |
| G9 | **Wage-payment timing not tracked** *(new)* — Code on Wages requires wages paid by the **7th of the following month**. Not enforced anywhere. | Out of scope for the *computation* engine, but **surface a due-date field** on the payroll run (a #855 concern) and flag here so it isn't lost. No engine change in #854. |
| G10 | **Attendance/`presentDays` data source undefined** *(new)* — the engine consumes presentDays but the spec never says where it comes from (manual entry? leave module? attendance integration?). | **Define the input contract in #854-A**: presentDays/workingDays are inputs to the engine (manual entry in #854-B for MVP; integration point documented for later). Engine stays pure — it computes from whatever it's given. Name the MVP source (HR manual entry per slip) so #854-B builds the field. |

## 3. Open decisions for the owner (decide before #854-A starts)

1. 🟠 **G5 — Employer Contribution slip default.** Recommend **`true`** (honors ticket's "for
   transparency"), toggleable. Confirm or override.
2. 🟠 **G7 — LOP basis default.** Recommend **`actual_working_days`**. Confirm this matches your
   attendance/leave policy (some firms standardise on 26).
3. 🟠 **Gratuity basis (affects #855 CTC view, not #854).** Under the Labour Codes 50% floor, gratuity
   (15 × wages / 26) should use the **wage floor**, not raw Basic. If #855 still computes off Basic,
   the CTC view is *understated*. Decide: fix now in #855, or ship as a **known approximation** flagged
   for CA review. Recommend flag-now, fix-in-#855.

## 5. Compliance correctness — what's locked (from spec §1–2)

Non-negotiables already designed in; listed here so the plan is self-contained:

- **Labour Codes 2025 50% wage floor** — `pfBasis = max(basicAfterLOP, 0.50 × grossAfterLOP)` before
  the ₹15,000 restricted cap. Default structure Basic = 50%. Without this the MVP is non-compliant
  from day one.
- **ESI period coverage** — once covered at period start (Apr–Sep / Oct–Mar), keep deducting to
  period end even if gross crosses ₹21,000 (the *correct* direction; the original spec had it
  backwards). Backfill per G2.
- **Effective-dated `statutory_rates`** — every rate resolved *as of the slip period*, never "now."
- **Computation snapshot on every slip** — persist inputs + rules + resolved rates + itemised output
  as JSONB, so a regenerated historical slip reproduces the original numbers (audit-critical).
- **State deductions registered/not-registered flag** — deduct where registered; elsewhere deduct ₹0
  **but flag on the internal exposure report** so the gap is visible and reversible.
- **Punjab PSDT** seeded (the one live state levy your cluster triggers); Delhi/UP/Bihar seeded at
  ₹0; MH/KA/TN/WB/TG seeded but `is_registered = false`.
- **Jammu & Kashmir + Ladakh (see spec §2.4 for the full treatment)** — three build-relevant facts:
  **(a)** both UTs are **PT-exempt → seed each at ₹0** (like Delhi/UP/Bihar), and store **Ladakh as a
  separate UT** from J&K in the `state_deductions` / `pt_state` values, not merged;
  **(b)** PF is **fully central since 1 Jan 2020** (J&K was excluded from the EPF Act before that and
  ran its own PF) — so **no engine change**, HQ registration covers it, and the *effective-dated*
  design is what keeps a pre-2020 J&K slip correct (no PF then) if ever regenerated;
  **(c)** ESI applicability in J&K is **area-dependent** (ESIC-implemented areas only), which is
  handled by the existing **`esi_applicable`** per-employee flag — set it by locality; the engine
  respects it. Net: J&K/Ladakh add **two ₹0 seed rows and zero engine logic**.
- **`jurisdiction` column** on structures + rate/slab tables (default `'IN'`) and a **locale-aware
  formatter** for ₹ grouping — the cheap seams that make country #2 an add, not a rewrite.

## 6. Top-1% product layer — what makes it *easy to use*, not just correct

Compliance gets you legal. These get you loved. Payroll's core UX problem is **trust**: employees
dispute numbers they can't understand, and HR fears the "generate" button. Every principle below
attacks that.

**6.1 Show-your-work transparency (the flagship feature).**
Every figure on a slip is **explainable on click** — inputs, formula, and the *rate version used*
(you already snapshot this; surface it). "Employee PF ₹1,800 = 12% × min(₹18,000 Basic-after-LOP,
₹15,000 ceiling) · restricted mode · EPF Act rate effective 2014." This single feature eliminates the
majority of payroll disputes and is what separates enterprise-grade from a spreadsheet.

**6.2 Preview-before-commit, always.**
Generation is a two-step: **preview → confirm**. Never surprise HR. The preview shows a **diff vs last
month** with plain-language reasons: "Net pay ↓ ₹2,400 — cause: 3 days LOP (Basic, HRA, Conveyance
prorated)." A payroll tool that can't explain a delta is a payroll tool people don't trust.

**6.3 Error prevention over error messages.**
Validate structures at *creation*, not at generation: enforce dependency ordering (HRA needs Basic
first), require a residual absorber, and show the **persistent** Basic-<50% banner (a banner, not a
dismissible toast — HR dismisses toasts and forgets). Don't let a broken structure exist.

**6.4 Progressive disclosure.**
Default screen is dead simple: assign structure → preview → generate. PF mode, state registrations,
slab overrides, LOP basis live **one layer down** in Settings. Don't put statutory knobs on the daily
path. Executives configuring compliance and HR running monthly payroll are different jobs — design for
both without making either wade through the other's controls.

**6.5 Audit trail as a first-class surface.**
Every override (with reason), every rate change, every regeneration — logged with who/when/why and
**visible**, not buried. Regenerating a slip that's already been shared or paid triggers a warning;
the snapshot preserves the original. This is what survives due diligence and inspections.

**6.6 Proactive compliance, not reactive.**
The tool tells you what's coming: "ESI contribution period ends 30 Sep — 3 employees will be
re-evaluated." "You have 4 Punjab employees but PSDT registration is marked *not registered* —
₹800/mo unremitted exposure." "EPF ceiling change is under Supreme Court review — watch for
notification." Top tools nudge; functional ones wait to be asked.

**6.7 Config-change impact preview.**
Flipping PF mode to unrestricted, or registering a new PT state, shows **who and how much** before
apply: "Affects 14 employees · +₹X/mo employer cost · net pay unchanged." No silent blast-radius.

**6.8 First-run experience.**
Ship with the seeded "Standard" structure **already working**, not a blank config screen. HR should
generate a correct slip within minutes of first login, then customise — never stare at an empty
rule builder wondering what a "residual absorber" is.

**6.9 Explain-to-employee mode.**
A plain-language slip employees actually understand (what PF is, why ESI is deducted, what "LOP" did
to this month), mobile-friendly. Every question this answers is an HR support ticket that never gets
filed.

**6.10 Graceful fallback (already in spec — keep it).**
The unstructured/manual path always works. New structure engine for those who want it; manual for edge
cases and mid-month joins. Never a dead end.

> **Sequencing note:** 6.1, 6.2, 6.3, 6.8, 6.10 are **MVP-defining** — build them into #854-B.
> 6.5 is largely free because the snapshot + override-reason data already exists; just surface it.
> 6.6, 6.7, 6.9 are **fast-follow** (Phase 2) — real differentiators, but don't block launch.

## 7. Execution sequence (Replit build order)

**#854-A — Engine (compliance-critical, do first, in this order):**
1. `statutory_rates` effective-dated table + resolver *(engine depends on it — first)*.
2. Schema migrations: `state_deductions` (+ `is_flat` G6, `psdt_annual_threshold` G1), employee
   fields (`pt_state`, `work_city` +comment G4, `esi_applicable`, `esi_covered_until`, disability),
   `salary_structures` (+ `jurisdiction`), `salary_slips.computation_snapshot`, `lop_basis` +
   `show_employer_contribution_on_slip` in settings.
3. **ESI backfill migration** (G2) — with affected-set logging.
4. **Seed `state_deductions`:** Punjab PSDT (with `psdt_annual_threshold`), Delhi/UP/Bihar + **J&K +
   Ladakh (separate UTs, ₹0)** as no-levy rows, MH/KA/TN/WB/TG with `is_registered = false`. Seed
   `statutory_rates` (PF/EPS/EDLI/ESI + ceilings) with `effective_from` dates per CA.
5. `computeComponentsFromGross` (country-agnostic, pure) — dependency-ordered rules, residual absorber,
   `lop_basis` semantics (G7), rounding reconciliation (G8).
6. `computeIndiaStatutory` behind the `StatutoryEngine` interface — 50% floor, PF caps/splits, ESI
   period logic, flat-vs-proportional state deductions.
7. Wire into generate/regenerate; write computation snapshot; keep unstructured path intact.
8. **Golden vectors as automated tests** — print computed-vs-expected table for CA eyeballing.
9. 🔒 **Gate: CA confirms expected outputs → vectors pass → #854-A done.**

> Instruct the Replit agent explicitly: *"Statutory numbers come from `statutory_rates` resolved by
> pay period — never hard-code ₹15000/₹21000/₹1250/12%/0.75%. Keep `IndiaStatutoryEngine` behind the
> generic `StatutoryEngine` interface. Write the golden vectors as passing tests before wiring slip
> generation."* Agents love to inline rates and scaffold UI early — both defeat the point.

**#854-B — UI / PDF / Settings (starts once engine interface is stable):**
9. Salary Structures tab: list, rule builder, **live preview**, PF mode toggle (per structure).
10. State Registrations panel (registered/not-registered → deduct-vs-flag).
11. Slip form: auto-filled read-only fields + per-field **Override** toggle (requires audit reason).
12. `salarySlipHtml.ts`: Earnings / Deductions / Employer Contribution (toggle G5) / Net Pay via
    locale formatter.
13. My Team: assign structure + set PF-exempt / disability / ESI-applicable / pt_state.
14. **Top-1% MVP UX** (§6): show-your-work (6.1), preview+diff (6.2), creation-time validation +
    persistent 50% banner (6.3), working first-run (6.8).

**Phase 2 fast-follows:** proactive compliance nudges (6.6), config-change impact preview (6.7),
explain-to-employee mode (6.9), LWF (state-keyed table already ready), bulk payroll run (#855),
executive compliance dashboard, gratuity-basis fix.

## 8. Pre-production checklist — HARD GATE before first live run

*(Promoted from a §12 footnote — this is a gate, not a note. No real employee payroll runs until every
box is checked.)*

- ☐ CA has signed off on `statutory_rates` seed **and** golden-vector expected outputs.
- ☐ CA has confirmed PSDT threshold (G1), EPF rounding (G8), EPF admin min (G3), PT seed values.
- ☐ ESI backfill migration run; affected-set log reviewed by HR (G2).
- ☐ LOP basis (G7) confirmed against company attendance policy.
- ☐ Employer-contribution slip default (G5) confirmed by owner.
- ☐ Gratuity-basis approximation (§3.3) documented for CA if not yet fixed in #855.
- ☐ Punjab PSDT registration status set correctly in State Registrations; exposure report reviewed.
- ☐ If hiring in **J&K/Ladakh**: ₹0 PT seed rows present (Ladakh stored separately), and
  **`esi_applicable` set per employee by locality** (ESIC-implemented area or not) — see spec §2.4.
- ☐ Golden vectors pass, including boundary cases: gross = ₹21,000 exactly, EPS cap at basis >
  ₹15k unrestricted, 50%-floor trigger at Basic 40%, ESI mid-period crossing, disability flag,
  pf_exempt, flat-levy no-proration (G6), rounding reconciliation (G8).
- ☐ Regeneration of a historical slip reproduces original numbers (snapshot verified).
- ☐ **Data residency & access controls** for salary/PII on the hosting environment reviewed and
  accepted (relevant if running on Replit or any cloud).
- ☐ Rate tables placed under change control (who can edit, logged).
