# REPLIT WORK ORDER

## Hire’in Current-System Audit for CEO Copilot and AI Governance Layer

## 1. Role

Act as a senior SaaS solution architect, business analyst, systems analyst, security architect, AI-governance architect and codebase auditor.

You are reviewing the existing Hire’in operating platform before we design and implement a company-wide CEO Copilot and AI Governance Layer.

This is a **discovery and audit assignment only**.

Do not implement the CEO Copilot during this assignment.

Hire’in already has a substantial internal employee and company-management platform.

The system may already contain some or all of the following:

* Employee profiles
* Reporting hierarchy
* Departments, roles and levels
* Goals and KPIs
* Training plans
* Probation plans
* Performance improvement plans
* SOPs and policy acknowledgements
* Weekly or periodic check-ins
* Manager feedback

* Escalations

* Approvals
* Employee concerns or tickets
* Audit logs
* Reports and dashboards
* Tasks and follow-ups
* Sales, staffing, recruiting or delivery modules
* Marketing or content modules
* Financial or operational reporting
* AI or LLM integrations

Some modules already contain their own mini-notifications and automations.

The future CEO Copilot must **reuse and govern what already exists**, not rebuild working modules unnecessarily.

The intended future system is a privacy-preserving governance and intelligence layer that:

* Enforces management hierarchy
* Monitors whether existing processes are followed
* Audits goals, check-ins, SOPs, training, probation and PIPs
* Audits managers as well as employees
* Correlates facts across modules
* Identifies missing actions and broken process chains
* Supports employee questions and concerns
* Produces fact-based findings
* Provides recommendations and decision packets to the CEO
* Keeps consequential employment and business decisions with humans
* Prevents PII and restricted employee data from being sent to external AI systems
* Uses deterministic rules wherever AI is unnecessary
* Remains model-provider-agnostic and cost-efficient

# 3. Non-negotiable audit rules

## 3.1 Source of truth

Use this order of authority:

1. Current running application code
2. Current database schema and migrations
3. Current runtime configuration
4. Current API routes and services
5. Current active jobs, schedulers and event handlers
6. Current tests
7. Current UI behavior
8. Repository documentation
9. Historical plans or archived documents

Do not claim that a feature exists merely because a document says it exists.

Verify that it exists in live code and, where safely possible, in the current schema.

For every capability, classify it as:

* `VERIFIED_ACTIVE`
* `VERIFIED_PARTIAL`
* `PRESENT_BUT_NOT_CONNECTED`
* `DOCUMENTED_ONLY`
* `DEPRECATED`
* `DUPLICATED`
* `NOT_FOUND`
* `UNABLE_TO_VERIFY`

## 3.2 Read-only audit

Do not:

* Change production code
* Refactor modules
* Modify schemas
* Run database migrations
* Change environment variables
* Enable or disable jobs
* Send notifications
* Create employee records
* Update goals, PIPs or check-ins
* Trigger payroll
* Modify production data
* Add AI integrations
* Expose secrets
* Print raw PII
* Commit implementation changes

The only permitted repository changes are audit documents placed under:

```text
docs/ceo-copilot-system-audit/
```

If a helper script is absolutely required, it must:

* Be read-only
* Be placed under `docs/ceo-copilot-system-audit/tools/`
* Never print secrets or PII
* Never perform INSERT, UPDATE, DELETE, ALTER, DROP or migration operations
* Be documented in the audit report

Record the Git status before and after the audit.

## 3.3 Privacy

Do not copy real employee PII into audit documents.

Never include:

* Names
* Personal email addresses
* Phone numbers
* Home addresses
* Dates of birth
* Government identifiers
* Tax identifiers
* Bank information
* Payroll documents
* Medical information
* Passwords
* API keys
* Tokens
* Session cookies
* Encryption keys
* Private complaint text
* Investigation records

Use pseudonymous examples such as:

```text
EMP-001
MGR-002
DEPT-HEALTHCARE
PLAN-PIP-003
```

Environment variable names may be documented, but their values must never be displayed.

## 3.4 Evidence standard

Every material audit statement must include at least one technical reference:

* File path and line range
* Database table and column
* Migration name
* API route
* Service or function name
* Scheduler or job name
* UI route or component
* Test reference
* Runtime configuration reference

Mark every statement as:

* `VERIFIED`
* `INFERRED`
* `UNVERIFIED`

Do not hide uncertainty.

* The current schema has been inspected.

* Notification delivery is separated from action completion.

* PII fields and decryption points are identified.
* Existing AI usage is documented.
* Every material claim links to evidence.
* Unknowns remain explicitly marked.
* No production logic or data is changed.
* The resulting documents contain sufficient information to design the CEO Governance Layer without guessing.
