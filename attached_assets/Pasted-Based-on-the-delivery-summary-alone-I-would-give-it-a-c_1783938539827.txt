The delivery summary does not mention a DISCARDED hook.

If Content Studio has an existing discard, reject, or abandon action, wire it now.

This is a meaningful signal because rejected drafts often reveal more than accepted drafts.

2. Confirm whether social-kit outcomes were included

The summary mentions article routes, but it does not explicitly mention the social-kit flow.

Verify whether these events are captured for social kits:

Accepted
Edited then accepted
Discarded
Regenerated

If the social-kit flow is not stable yet, document it as a limitation rather than pretending it is complete.

3. Verify the access-control interpretation

This line needs careful checking:

employees/executives blocked

BD recruiters, salespeople, content creators, and managers who actually use the agents must be able to submit feedback on records they are authorized to see.

The correct behavior should be:

A BD user can rate an accessible BD message
A Content user can generate outcome events for accessible Studio records
An administrator or authorized manager can use the summary endpoint
A user cannot submit feedback against another inaccessible conversation or article

Do not block ordinary authorized users merely because they do not have an elevated Studio role.

4. Add database-level uniqueness for ratings

Service-level idempotency is good, but concurrent clicks or retries can still race.

There should be a database constraint or safe upsert pattern guaranteeing one active rating per:

user
+ agent type
+ source record type
+ source record ID

A user changing from positive to negative should update the existing rating, not create two records.

The 30-second action deduplication is acceptable for the MVP, provided it uses a stable idempotency rule and does not suppress legitimate actions on different records.

5. Validate EDITED_THEN_ACCEPTED

Comparing bodyMarkdown with generationV1Markdown is directionally correct.

But confirm that formatting-only changes do not always produce EDITED_THEN_ACCEPTED, such as:

Line-break changes
Trailing spaces
Markdown normalization
Case-only changes
Editor serialization differences

For tomorrow, a simple normalized comparison is sufficient. You do not need an edit-percentage engine.

6. Confirm prompt and model versions reach the events

The service may support those fields, but verify the actual call sites populate them when available.

This will be critical later when you ask:

Did quality improve after prompt version 6?

Without prompt-version metadata, historical feedback becomes much less useful.

7. Confirm feedback failure does not break user actions

Saving an idea, generating a deck, publishing, or accepting a draft must succeed even if feedback logging fails.

The correct behavior is:

Primary action succeeds
→ feedback event attempted
→ failure logged for retry or investigation
→ user workflow is not blocked
Not required before tomorrow
