What the plan gets right
Credit where due, because these choices matter: the planning layer as a first-class entity (rather than pretending drafts are plans) is the correct architecture and directly solves the "team retreats to Excel" problem. The family split avoids the type-explosion trap. Brand voice as a JSON config per project instead of a new table is right-sized. Reusing the existing notification table, email gateway, and scheduler patterns instead of building parallel infrastructure is exactly what a codebase-aware architect should do. And the out-of-scope lines (no external publishing APIs, no CRM, no WebSockets) show real scope discipline.
Design flaws to fix before dev
1. The import will silently drop data against #906's schema. Your Excel template carries Caption/Copy, Requirement, Final Creative, and four Story columns. studio_content_ideas has none of these fields — only topic, brief, referenceLink. And since #906 correctly makes instagram_story its own content type, an Excel row containing both post and story content must split into two linked ideas, which no document specifies. Fix in the spec: add captionCopy, requirement, creativeLink to the ideas schema; add a groupId (or parentIdeaId) so the post-idea and story-idea from one row stay linked; define the Status/Publish → status enum mapping with unmapped values surfacing as row errors in the preview. Also still unanswered from my first review: the dedupe rule. Importing the same sheet twice must not duplicate everything — either match on Date+Topic (skip/update) or, simpler and very practical, stamp every imported row with an importBatchId so a bad import is reversible in one action.
2. The AI brief is being stuffed into bodyMd — that's a smell. #906 Step 6 pre-fills the article body with the structured brief. But bodyMd is the content: when generation runs, it either overwrites the brief (context lost) or appends around it (brief pollutes the draft). Put the brief in a dedicated field (generationBrief or similar) that aiDraftService reads as context, keeping bodyMd for actual output. And note what got dropped from my earlier review: both docs dump the raw discussion thread into the brief. Acceptable for v1, but noisy threads ("ok", "see above", reversed decisions) produce noisy generations — keep the Brief Compiler (AI-condensed brief, user confirms before generation) on the near-term backlog.
3. Comments as a JSON array column will bite within a month. No per-comment IDs means no edit, delete, or resolve. Concurrent appends from two users can lose an update unless you use atomic jsonb operations. And notice the gap in the notification wiring: T1 fires on assignment, review, decision, deadline — but not on new comments, which is the main collaboration loop of the discussion feature. A small studio_idea_comments table (id, ideaId, userId, message, resolvedAt, createdAt) costs one migration now and enables comment notifications, resolve-state, and the Brief Compiler later.
4. The real blog_post defect is server-side, and neither doc fixes it there. Both specs fix the client to send a valid type. But the deeper defect is that the API accepted an invalid contentType and the AI service failed silently — #906's own What & Why says so. Add server-side enum validation (400 on unknown type) and make aiDraftService fail loud with an explicit "no prompt template for type X" error. Otherwise this exact bug class recurs the next time anyone adds a type.
5. Promote-to-Article is undefined for the Social family. #905's out-of-scope says social types don't get full article generation; #906's promote endpoint doesn't restate that restriction. What does "Create Article" do on an approved instagram_post idea? Either hide/block promote for social family, or route it to social-kit/caption generation. Pick one and write it down, or you'll get a runtime surprise.
6. No status sync-back from article to idea — this breaks T2's progress bars. linkedArticleId creates the link, but nothing flips the idea to done when the article publishes. Campaign completion percentages in #907 will permanently undercount. One line in the publish transition handler fixes it; add it to T1's steps.
7. T3's click tracking, as specified, will record zero events. This is the biggest technical flaw in the set. UTM parameters on outbound CTA links attribute traffic in the destination's analytics — they don't call your /api/track/click endpoint. Nothing in the spec connects the UTM-tagged links to the events table. Fix: either rewrite CTAs to route through your endpoint as a 302 redirect (/api/track/click?...&redirect=<url>), or add a small beacon script on the public Insights pages that fires the endpoint reading the UTM params. Relatedly, don't mutate the stored bodyMd on publish to inject UTMs — edit-republish cycles and campaign changes will bake stale parameters into content. Inject at render/serve time instead.
8. Two notification-layer subtleties in T3. First, "update the two common notification-send patterns" is fragile — centralize into a single notify() gateway that checks preferences, so every future call site (including T2's campaign events) inherits the behavior instead of needing to remember it. Second, the weekly digest queries users with emailEnabled = true — but the default is opt-in with no row existing. If that query is implemented as a join requiring a row, nobody who hasn't touched preferences gets a digest. The query must treat "no row" as enabled.
9. Still unanswered from round one: transition permissions. Who can Approve/Reject/Assign ideas? The notification wiring references CM/marketing roles but the idea endpoints specify no role checks. Also minor: the digest job hardcodes four role names — verify they match the actual role strings in your system, and confirm whether X/Twitter belongs in the social type list, since your channel mix discussion earlier included it.
