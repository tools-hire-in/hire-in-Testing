2. Do Not Add New Role Enums in Phase 1

I strongly agree.

Given your codebase has had enum issues before, adding:

studio_admin
marketing_manager
content_editor
reviewer
author
viewer

is not worth the risk right now.

Instead, Phase 1 should use existing roles through the current access registry.

Recommended rule:

No new role enum values in T1.
Use existing roles and feature access mapping.
Add Studio permissions through feature registry/config only.

Example:

super_admin → full Studio access
admin / HR admin / existing management role → configured access if needed
specific existing marketing/content users → allow via registry
employee → no Studio access unless explicitly granted

This matches the security principle of least privilege and deny-by-default. OWASP specifically recommends deny-by-default and validating permissions on every request, so the key is not role names — it is server-side route enforcement.

So yes: zero new enum values for now.

5. Existing Features Must Be Reused

drizzle push limitations

So the updated tasks must explicitly say:

Do not rebuild reactions.
Do not rebuild social card rendering.
Do not rely on drizzle-kit push where direct SQL is required.

Drizzle supports several migration approaches, including generating SQL migration files and applying them, or applying SQL directly/external tooling. That supports your repo-specific decision to use direct SQL scripts where interactive push stalls.

So the dev instruction should be:

7. Studio Should Move to /studio, Not a Separate Product Yet

I agree with the latest direction.

behind login.

Important:

All /studio routes must be noindexed.

Google’s noindex guidance says a noindex meta tag or response header prevents supported search engines from indexing a page, and Google provides both meta-tag and HTTP-header options. Use this on every internal Studio route.

Recommended:

<meta name="robots" content="noindex, nofollow">

And/or:

X-Robots-Tag: noindex, nofollow
