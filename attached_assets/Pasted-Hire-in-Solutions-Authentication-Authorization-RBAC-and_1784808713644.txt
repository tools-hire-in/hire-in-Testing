Hire’in Solutions

Authentication, Authorization, RBAC, and SOP Access Architecture

Revised Replit Implementation Recommendation

Document status: Final revised architecture recommendationPlatform: Hire’in Employee and Operations PortalDeployment context: Replit-hosted Node.js / Express / React / TypeScript / PostgreSQL applicationArchitecture stage: Single-company internal platform with future commercialization potentialVersion: 2.0Date: July 2026

1. Executive Summary

Hire’in Solutions does not currently need a complete authorization rewrite or an immediate multi-tenant redesign.

The immediate problem is narrower and more urgent:

The system already has a centralized authorization foundation in shared/accessControl.ts.

Many parts of the application still bypass that system and use inline role arrays, free-text concepts, or feature-specific checks.

SOP visibility is broken because rollout scope and role-assignment seed data do not match the real users.

account_manager appears as though it is a system role even though the database role enum cannot store it.

Existing product-specific access, such as studioAddOn, is useful but remains a one-off access pattern.

Designation, department, public title, author profile, job function, and authorization role are still being interpreted inconsistently.

The recommended solution is therefore:

Fix the immediate SOP and ghost-role defects first, then make the existing centralized access-control registry the single source of truth for authorization.

A normalized permissions and multi-role model should follow only after the centralized access layer is consistently adopted.

Multi-tenancy should not be implemented now. It should be treated as a separate future architecture programme, triggered by a confirmed external-customer requirement and explicit business approval.

3. What Was Correct in the Original RBAC Diagnosis

The original diagnosis correctly identified the following root issues.

3.1 Three different concepts are being called “role”

The system currently mixes:

System permission role

Employment designation

Business function slug

Examples include:

admin_users.role

admin_users.designation

account_manager

ta_account_manager

delivery_specialist

These concepts serve different purposes and must not be used interchangeably.

3.2 account_manager is a ghost system role

The current database role enum reportedly contains:

super_admin
admin
hr
finance
operations
manager
recruiter
employee
executive
director

account_manager is not a valid enum value.

However, it appears in live conditions such as:

["recruiter", "operations", "account_manager"].includes(user?.role || "")

This creates dead or misleading access logic.

account_manager may remain valid as:

A position

A designation

A business function

A template key

A job-function identifier

It must not be checked as a stored system role unless the authorization model is deliberately changed later.

3.3 SOP assignment is being confused with SOP progress

The existing behavior reportedly includes logic equivalent to:

if (progress.length === 0) return [];

That is architecturally incorrect.

An SOP assignment must exist before progress begins.

Correct sequence:

Audience rule
    ↓
Assignment created
    ↓
User sees assignment
    ↓
Progress starts
    ↓
Acknowledgment or completion recorded

A user with no progress record must still see an assigned SOP.

3.4 Rollout is being used as more than rollout

The current rollout configuration reportedly resembles:

{
  "mode": "pilot",
  "roles": [],
  "userIds": []
}

This setting is currently involved in visibility decisions.

A rollout setting should determine:

Whether a feature or SOP wave is released

Which audience receives it

When it becomes active

It should not permanently define authorization permissions.

4. Corrections to the Earlier Architecture Recommendation

The previous recommendation requires the following corrections.

4.1 Do not implement multi-tenancy now

The platform currently serves Hire’in Solutions as an internal system.

Introducing:

tenants

tenant_memberships

Tenant-scoped sessions

Tenant-scoped access rules

Tenant filters on every business query

Tenant-specific migrations or configuration

would be a major product-architecture programme.

This work should be deferred until:

There is at least one confirmed external-customer deployment model.

The commercial model is approved.

Data-isolation requirements are known.

Customer-admin behavior is defined.

Shared-database versus separate-database strategy is decided.

White-label, billing, and support-access requirements are understood.

For the current refactor, the system should remain single-company and single-tenant.

The code should still avoid unnecessary assumptions that would make future tenancy impossible, but no tenant tables should be added now.

4.2 Do not rebuild central authorization from scratch

The codebase already contains:

shared/accessControl.ts

ACCESS_REGISTRY

CENTRALIZED_ACCESS_CONTROL

requirePermission()

An admin override mechanism backed by system_settings

Therefore, the immediate target is:

Adopt, harden, and enforce the existing centralized access-control system everywhere.

The architecture work should begin with a real audit of that existing implementation.

4.3 Do not implement an admin SOP bypass

The SOP problem has two different causes:

Cause 1 — Rollout gate failure

Users such as hr and manager may fail resolveSopAccessForUser() because their roles are not included in the current pilot configuration.

Cause 2 — Assignment seed gap

Even users who pass the rollout gate may have no assignments because sop_role_assignments contains entries only for limited roles such as:

recruiter

operations

If no role assignment exists, the sync engine does not create the required user assignment or progress records.

The correct fix is:

Repair rollout scope.

Add the missing assignment seed rules.

Run idempotent assignment synchronization.

Keep administrative SOP management separate from personal SOP assignments.

4.4 Treat the full transformation as a programme

The long-term authorization modernization is not a single refactor task.

It should be planned across multiple stages with explicit scope and approval.

5. Confirmed Business and Access Decisions

5.1 One employee may perform multiple functions

A user may simultaneously be:

Recruiter

Account Manager

People Manager

Content Reviewer

BD contributor

This confirms that one role column will eventually be insufficient.

However, the system should not immediately replace the current enum.

The safer sequence is:

Centralize access checks.

Define stable permission codes.

Make modules depend on permissions rather than role names.

Introduce multi-role assignments later behind the same permission interface.

5.2 Managers may access direct reports only

Manager access must be relationship-scoped.

The authorization rule should be:

User has the required manager permission
AND
Target employee’s manager_user_id equals current user ID

Example:

employee.read_direct_reports

The manager role alone must not allow access to:

Peers

Other managers’ reports

Indirect reports

Former reports

Entire departments

Entire company records

Any future reporting-tree access should use a separate permission.

5.3 Admin users manage SOPs but do not inherit every SOP

Administrators should be able to:

Manage SOP catalog

Publish SOP versions

Create assignments

Monitor completion

Send reminders

Escalate overdue obligations

Export compliance results

Enforce acknowledgment

Administrators should not automatically receive every SOP as a personal assignment.

Separate views are required:

My SOPs
Team SOP Compliance
All SOP Compliance
SOP Catalog
Rollout Management

5.4 Operations is not Admin

Operations should remain:

A department

A business function

A possible operational authorization bundle

It should not automatically receive:

User-management permissions

Role-assignment permissions

Security-setting access

Global configuration access

Unrestricted audit access

Full SOP administration

Example:

Department: Operations
Designation: Junior Operations Engineer
Business function: operational_support
Temporary authorization role: operations

5.5 Account Manager is primarily a position or function

Account Manager should not be introduced as a system role merely because the title contains “Manager.”

Possible metadata:

Designation: Account Manager
Business function: account_management
Department: Client Delivery

A person receives management access only if they have direct reports and the required manager permission.

A person receives recruiting access only if they are assigned recruiting permissions.

5.6 Guest author and reviewer access is article-specific

A guest may be invited to:

View one article

Comment on one article

Provide feedback

Appear on the author or contributor profile tag

A guest should not automatically receive:

Full Content Studio access

Access to unrelated articles

Publish rights

Delete rights

User-management rights

Access to other product modules

5.7 Tool access may be assigned independently

The following may be independently enabled:

Content Studio

BD Tool

CEIPAL functionality

SOP Governance

Future internal products

However, this should not result in separate uncontrolled boolean checks across the application.

The existing studioAddOn pattern should be centralized first, then generalized later.

7.2 Permission checks must include scope

A simple yes/no permission is insufficient for many records.

Own-record scope

Permission: employee.profile.read_own
Condition: target.user_id = current user ID

Direct-report scope

Permission: employee.read_direct_reports
Condition: target.manager_user_id = current user ID

Specific-article scope

Permission: content.article.comment
Condition: active collaborator record exists for this article and user

Assigned-record scope

Permission: bd.lead.update_assigned
Condition: lead.assigned_to = current user ID

12. Content Studio and studioAddOn

12.1 Current pattern

The system already uses:

adminUsers.studioAddOn

to grant Content Studio access independently of the base role.

This is a useful pattern because it confirms that:

Product access is not the same as employment role.

A user may require optional module access.

12.2 Immediate recommendation

Do not create a parallel generic product-membership table yet.

Instead, centralize the existing behavior:

hasProductAccess(user, "content_studio")

or:

requirePermission("content_studio.access")

The resolver may internally read studioAddOn during the transition.

12.3 Future generalization trigger

Create a generalized product-access model only when:

Several products need independent access

Product lifecycle is consistent

Activation, expiration, suspension, and audit requirements are shared

One-off fields are becoming difficult to maintain

Possible future model:

user_product_access
- user_id
- product_code
- status
- effective_from
- expires_at
- assigned_by
- reason

That future model should replace studioAddOn, not exist alongside it indefinitely.

24. Final Recommendation

Hire’in Solutions should not start with a full RBAC rewrite or multi-tenant redesign.

The correct architecture path is:

Fix current SOP and ghost-role defects
        ↓
Make existing accessControl.ts authoritative
        ↓
Remove scattered inline authorization
        ↓
Add stable permissions and scope checks
        ↓
Introduce multi-role assignments behind the same interface
        ↓
Modernize SOP governance and product access
        ↓
Evaluate multi-tenancy only after real external demand

The most important near-term rule is:

One centralized access-control registry must decide authorization. Designation, department, public title, business-function slug, SOP rollout, and author profile must never independently grant system access.

This approach fixes the current production problem, reduces security risk, preserves the existing Replit application, avoids a premature rewrite, and leaves a practical path toward a future commercial platform.
